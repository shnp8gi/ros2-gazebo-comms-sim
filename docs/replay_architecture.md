# 事後再計算 (replay) の設計と適用限界

作成 2026-08-03

## なぜ事後再計算にしたか

実行時評価では制御プレーンを別プロセスの ROS ノードとして非同期に動かしていた。
このため計画が効き始めるシム時刻が計算機の混み具合で変わり、**外部プロセスで
動く手法だけが負荷で不利になる**という交絡が生じていた。

実測 (競合条件、同一シード、並列 4 → 8):

| アーム | grant 時間の変化 |
|---|---:|
| assoc_hold (プラグイン内で完結) | +2.6% |
| KKF (外部 ROS ノード) | **−4.6%** |

交絡の大きさが手法間の差 (5〜14%) と同程度で、**同じ実験を 2 回やると結論が
変わる**状態だった。実際、KKF vs assoc_hold は本評価で +14.4% (p=0.00195)、
独立したアブレーションで +5.1% (p=0.557) と、有意性が消えた。

通信計算は車両の運動に影響しない (`VehicleMotionController::CalculateCommand`
は運動状態と `dt` しか受け取らない)。したがって物理は「手法」に依存せず交通
実現にのみ依存する。軌跡と全ペア RSSI を一度記録すれば、通信とスケジューリング
は後から単一プロセスで再計算できる。

| | 実行時評価 | 事後再計算 |
|---|---|---|
| 決定性 | 負荷依存 | **構造的に決定的** |
| チャネル実現 | 手法ごとに微妙に異なる | **全手法で同一** (共通乱数の理想形) |
| Gazebo 実行回数 | 手法 × シード | **シードのみ** |
| 1 タスクの所要 | 約 60 分 | 約 1〜2 分 |

## 適用限界 — リアルタイム車両制御では使えない

**この方式は「通信が運動に影響しない」という前提の上にのみ成立する。**

以下のいずれかを導入した時点で軌跡が手法に依存するようになり、一度記録した
軌跡を使い回すことはできなくなる:

- 隊列走行 (前車との通信で車間制御)
- 接続維持のための速度調整
- 遠隔運転 (制御指令が通信路を通る)
- 協調合流・交差点制御

前提が破れているかは `tools/check_motion_independence.py` で検査できる。
異なる手法・同一シードで記録した軌跡が一致しなければ失敗する。**モデルに
制御則を足したら必ず走らせること。** 走らせないと、再生の結果は失敗ではなく
静かな誤りになる。

## リアルタイム制御が必要になったときの選択肢

### 案 A: 適用範囲で切り分ける

通信スケジューリングの研究には再生、協調制御の研究には実行時、と使い分ける。
現在の評価対象は前者なので当面はこれで足りる。

### 案 B: ステップ駆動の協調シミュレーション (本命)

1 つのプロセスが物理と制御の両方のステップを所有する:

```
while t < T:
    gazebo.step(dt)
    state = gazebo.read()
    cmd   = controller(state)   # 同一プロセス内で同期呼び出し
    gazebo.write(cmd)
```

構造的に決定的で、非同期メッセージングに由来する取りこぼしや位相ずれが原理的に
発生しない。

**なぜ lockstep が失敗したかの教訓**: Gazebo が主導権を握ったまま外部プロセスを
待たせる構成にしたため、シム時刻を止めている間は「待てば次の観測が来る」が
成り立たなくなり、メッセージ 1 通の取りこぼしが回復不能なデッドロックになった
(競合条件では毎秒 2160 通)。再送を入れても解消せず、KKF アームは 3 タスク ×
3 回の再試行がすべて自壊した。**主導権を外に出せば同じ問題は起きない。**

### 案 C: 反復法 (非推奨)

軌跡を記録 → 通信を再生 → 結果を次の運動シミュレーションに反映、を繰り返す。
結合が弱ければ収束するが収束保証がなく脆い。

## 実装で踏んだ落とし穴 (再発防止のため記録)

いずれも「時刻を鍵にデータを突き合わせる」まで表面化しなかった。

1. **累積加算による位相ずれ (3 箇所)** — 観測送信・姿勢記録・通信更新のいずれも
   `next += 周期` で次回時刻を決めており、各車の初回更新時刻が起点になっていた。
   走行ごとに位相が 1〜3 ms ずれ、時刻を鍵にした突き合わせが**全く成立しな
   かった** (共通時刻ゼロの車両があった)。すべてグリッド計算 `floor(t/周期+1)·周期`
   に統一した。

2. **早期打ち切りが grant 保持を見ていた** — 評価するリンクの集合が手法で変わり、
   状態を持つ共有 RNG (Rician フェージング) の消費がずれて、**RSSI 自体が最大
   20 dB 食い違っていた**。記録モードでは幾何のみで判定する。

3. **占有を解放しない** — `!any_grant_synced` のときの `Sync(-1)` を移植し忘れ、
   一度掴んだ車が圏外に出ても RSU を握り続けて 12 台中 10 台が配信ゼロになった。

4. **空メッセージが割当を消す** — 「今エポックは言うことがない」と「あなたには
   割り当てない」が区別されていなかった。

## 検証手順

```bash
# 1. 記録 (シードごとに1回)
#    simulation_overrides.record_poses_path と
#    comms_simulator_node.record_pairs_dir を指定して実行

# 2. 前提の検査 (制御則を足したときは必須)
python3 tools/check_motion_independence.py <armA>/poses.csv <armB>/poses.csv

# 3. 再生
python3 tools/replay_sim.py <rec_dir> --arm assoc_hold --out <out_dir>
```

実行時との一致は assoc_hold で確認済み: 総配信量 3631.455 MB が完全一致、
12 台中 10 台がデータ量・接続時間とも一致 (残差 <3e-5 MB = 丸め)。
