現行本番シナリオ (`road_10car`): 直線1車線に対象車10台 (y=0)、RSU 3台 60m間隔 (y=8.0)、
遮蔽用の一般車は **role: blocker 専用エンティティ** として y=2.5/4.5/6.0 の3車線に確率生成。
arm = lut / trend / kf / kkf_cold / kkf_conv / oracle。

**本シナリオでの本質的な差分は 3 点**:
1. 一般車が「別レーンの背景」ではなく **対象車と同じ交通流の中に混在** する (対象車自身も遮蔽体になる)。
2. RSU が **対象車と反対側の路側** にあり、**手前車線の大型車が奥車線の対象車を遮蔽** する構造を明示的に作る。
3. 比較対象が KKF 系ではなく **「HO なしの先取り」と「事後最適 (神視点)」の 2 極** である。

## 1. 道路幾何

### 1.1 座標系と車線

- x = 道路軸 (下り = +x 方向)、y = 横方向、RSU は **y > 0 側の路側** に設置。
- 車線幅 `lane_width` = 3.5 m。中央線 y = 0。
- **車線数は方向ごとに独立設定** (`lanes_near` / `lanes_far`)。今回は 1 + 1、将来 2 + 2。

RSU は **歩道の外側の端 (民地境界側)** に立てるポールに設置する。したがって RSU の y は
**道路断面から決まる** (現行 road_10car の y=8.0 は「対向3車線ぶんの遮蔽レーンを置いた
広い断面」の名残であり、片側1車線の断面には合わない)。

道路構造令 第4種 (都市部) の標準断面から積み上げる:

```
y_rsu = lanes_near · lane_width + shoulder + sidewalk
      = 1 × 3.5      + 0.5      + 2.0      = 6.0 m     (1+1)
      = 2 × 3.5      + 0.5      + 2.0      = 9.5 m     (2+2)
```

| 記号 | 意味 | 今回 (1+1) | 将来 (2+2) |
|---|---|---|---|
| `lane_width` | 車線幅員 (第4種第1級 3.25〜3.5) | 3.5 | 3.5 |
| `shoulder_m` | 路肩・側帯 | 0.5 | 0.5 |
| `sidewalk_m` | 歩道有効幅員 (標準2.0 / 歩行者多 3.5) | 2.0 | 2.0 |
| `lanes_near` | RSU 側 (下り, +x) の車線数 | 1 | 2 |
| `lanes_far` | RSU と反対側 (上り, −x) の車線数 | 1 | 2 |
| 近車線 y | `+(k+0.5)·w`, k=0.. | +1.75 | +1.75, +5.25 |
| 奥車線 y | `−(k+0.5)·w`, k=0.. | −1.75 | −1.75, −5.25 |
| **RSU y** | 歩道外側端 | **6.0** | **9.5** |
| RSU 高 | ポール設置高 (§1.2 の注意参照) | 2.5【実測】 | 2.5 |

対象車までの横距離 L は次のようになる (旧 y=8.0 との比較):

| | 近車線 (y=+1.75) | 奥車線 (y=−1.75) |
|---|---|---|
| y_rsu = 6.0 (本仕様) | L = **4.25 m** | L = **7.75 m** |
| y_rsu = 8.0 (旧) | L = 6.25 m | L = 9.75 m |

> **車線数を掃引する際の注意**: 上式で自動計算すると車線を増やしたとき y_rsu が動き、
> リンクバジェットまで変わって交絡する。**車線数掃引のときだけ y_rsu を固定値で明示指定**
> できるよう、`--rsu-y auto|<値>` の両対応にする。

### 1.2 視線高さの検算 (遮蔽が成立するか)

RSU アンテナ高 2.5 m、車載アンテナ高 1.35 m、RSU y = 6.0。視線の高さは y のみで決まる
(線分パラメータが y に線形のため、x 方向のずれによらない)。

奥車線の対象車 (y=−1.75, z=1.35) → RSU (y=6.0, z=2.5) の視線が、**近車線の遮蔽車の
車幅 (2.5 m, y ∈ [0.5, 3.0]) を横切る区間の高さ**:

| y | 視線高 [m] (y_rsu=6.0) | 参考: y_rsu=8.0 |
|---|---|---|
| 3.0 (遮蔽車の RSU 側の端) | 2.06 | 1.91 |
| 1.75 (車線中心) | **1.87** | 1.76 |
| 0.5 (遮蔽車の中央線側の端) | **1.68** | 1.62 |

| 遮蔽車の車高 | 判定 | 余裕 |
|---|---|---|
| 乗用車 1.5 m | 通す | **+0.18 m のみ** (最も薄いところ) |
| バス 3.2 m | **遮蔽** | 十分 |
| トラック 3.8 m | **遮蔽** | 十分 |

→ 「大型車のみが遮蔽する」構造は保たれ、**RSU を近づけたことで乗用車に対する余裕はむしろ増える**
(視線の交差点が RSU 寄り = 高い位置になるため)。専用の視線判定コードは不要。

#### ⚠ 乗用車 1.5 m は「通す/遮る」の境界すれすれ

余裕が **0.18 m しかない**。日本の都市部で実勢の多いミニバン・SUV (車高 1.7〜1.9 m) を
乗用車クラスに含めると **遮蔽する側に転ぶ**。これはシナリオの性格を大きく変える
(遮蔽発生率が跳ね上がり、「大型車のみが遮蔽」という前提が崩れる)。

対応案 (どれを採るか §8 未決定):

- (a) 現行どおり乗用車 = 1.5 m とし、**「低車高乗用車」の仮定**であることを論文に明記する。
- (b) 乗用車クラスを **セダン 1.5 m / ミニバン・SUV 1.8 m** に分割し、幾何に判定させる
  (実勢に忠実。車種構成に 1 クラス増えるだけでコード変更は不要)。
- (c) **RSU 高を上げる** — 下記。

#### RSU 高 2.5 m の再検討

歩道上の設置物には建築限界 (歩行者の頭上空間) があり、**2.5 m は下端としての最低ラインに近い**。
アンテナ**中心**が 2.5 m のポールは実際には成立しにくく、実勢は 3.0〜4.5 m。

RSU 高を 4.0 m にした場合の視線高 (奥車線リンク):

| y | 視線高 [m] |
|---|---|
| 3.0 | 2.98 |
| 1.75 | 2.55 |
| 0.5 | 2.12 |

→ 乗用車 1.5 m もミニバン 1.9 m も**余裕をもって通し**、バス 3.2 m / トラック 3.8 m は**確実に遮る**。
「大型車のみが遮蔽する」構造が**パラメータの微差に依存しなくなる**ため、
**RSU 高 3.5〜4.0 m を推奨**する。ただし 2.5 m は【実測】値として与えられているため、
実測の根拠 (何を測った値か) を確認してから変更したい (§8 未決定)。

### 1.3 RSU 配置とアンテナ角

- **4 台、10 m 間隔** → x = −15, −5, +5, +15 (中心対称)。全て y = 6.0 (歩道外側端)、アンテナ高 2.5 m。
- 角度規約 (現行踏襲): RSU yaw = −90° + δ_rsu。δ_rsu > 0 = ビームを **下流 (+x)** へ振る。
  δ_rsu < 0 = **上流 (−x)** へ振る。
- **2 台ずつ上流側・下流側に振る**。並び方は 2 案あり掃引変数 `rsu_tilt_pattern` とする:

| pattern | x=−15 | x=−5 | x=+5 | x=+15 | 狙い |
|---|---|---|---|---|---|
| `alternate` (推奨) | −δ | +δ | −δ | +δ | 上流窓・下流窓を空間的に交互配置 |
| `grouped` | −δ | −δ | +δ | +δ | 区間前半で上流窓、後半で下流窓 |

#### ⚠ 重要: δ = 15° は 10 m 間隔では機能しない

RSU から対象車までの横距離 L (奥車線で L = 7.75 m) に対し、ビーム中心が道路軸上で当たる位置は
`Δx = L·tan(δ_rsu)`。δ=15° なら **Δx = 2.1 m** で、4 台とも実質同じ場所を照らす
(RSU 間隔 10 m に対して窓が重なりきる)。**RSU を近づけたことで、この問題はさらに悪化する**
(L が小さいほど同じ δ で窓が近くに寄る)。

さらに **厳密な相互ボアサイト対向の条件**を導くと (RSU→車 と 車→RSU の視線ベクトルが
両者のボアサイトに一致する条件):

```
δ_veh = 90° − δ_rsu      (このとき対向成立)
対向が成立する位置       Δx = L · tan(δ_rsu)
```

- δ_rsu = δ_veh = **45°** → 奥車線 (L=7.75) で Δx = 7.75 m、近車線 (L=4.25) で Δx = 4.25 m。
  RSU 間隔 10 m とおおむね整合し、隣接セルの手前で対向がとれる。
- 奥車線の対向位置を RSU 間隔 10 m に正確に合わせたいなら δ_rsu = atan(10/7.75) = **52°**。
- 現行 `gen_road_scenario.py` の docstring にある「15°/15° では厳密対向は不成立」という
  注記は、この式で**解消できる** (δ_rsu + δ_veh = 90° にすればよい)。

→ **既定 δ_rsu = 45°, δ_veh = 45°**。δ ∈ {30, 45, 52, 60} を掃引変数として残す。

#### ⚠ 近車線と奥車線の非対称が拡大した

L の比 (奥/近) は **7.75/4.25 = 1.82** (旧 y=8.0 では 9.75/6.25 = 1.56)。
RSU を近づけたことで **奥車線は「遮蔽される」だけでなく「距離も遠い」** という
二重のハンデを負う。したがって:

**「近車線 vs 奥車線」の比較は、距離と遮蔽が交絡していて主張に使えない。**

制御された比較は次のいずれかにする:

- **同一車線内で「遮蔽あり run vs 遮蔽なし run」** (大型車比率 0 の対照条件を作る) — 推奨
- 同一車線内で「NLOS 区間 vs LOS 区間」のパス単位比較

車線別の集計 (§7 E2) は**現象の記述**には有用なので残すが、**利得の主張には使わない**。

### 1.4 車載アンテナの向き (方向別の符号反転)

対象車のアンテナは「RSU 側 (world +y) へ δ_veh 傾ける」。車体 yaw が方向で異なるため、
**relative_rpy の yaw は方向で符号が反転する**:

| 車線 | 車体 yaw | relative yaw | ボアサイト world yaw |
|---|---|---|---|
| 近 (下り, +x) | 0 | **+δ_veh** | +δ_veh |
| 奥 (上り, −x) | π | **−δ_veh** | 180° − δ_veh |

現行 `gen_road_scenario.py` は +δ 固定なので、対向車線を扱う際の**必須の修正点**。

## 2. 交通流 (対象車と一般車の混在)

### 2.1 生成モデル

各車線を独立のポアソン/対数正規到着列とし、**1 台引くごとに (車種, 通信対象か否か) を決める**。
現行 `traffic_gen.py` は blocker しか生成しないので、tx エンティティも生成できるよう拡張する。

```yaml
traffic:
  window_s: [0.0, 120.0]        # この時間窓に区間へ進入する車のみ生成
  corridor: [-60.0, 60.0]       # 通信が意味を持つ区間 [m]
  margin_m: 40.0
  warmup_s: 10.0                # 集計から除外する助走時間 (新規)
  target_ratio: 0.30            # 交通全体に占める通信対象の割合 (新規)
  vehicle_mix:                  # 都市部幹線の車種構成【要実測校正】
    - { model: Sedan, ratio: 0.80, height_m: 1.5, loss_db:  8.0, can_be_target: true  }
    - { model: Truck, ratio: 0.15, height_m: 3.8, loss_db: 26.0, can_be_target: false }
    - { model: Bus,   ratio: 0.05, height_m: 3.2, loss_db: 22.0, can_be_target: false }
  lanes:
    - { y:  1.75, direction: +1, speed_mps: 16.7, headway_s: {dist: lognormal, mean: 5.0, sigma: 0.6, min: 1.5} }
    - { y: -1.75, direction: -1, speed_mps: 16.7, headway_s: {dist: lognormal, mean: 5.0, sigma: 0.6, min: 1.5} }
```

- **通信対象は乗用車のみ** (確定)。`can_be_target: true` は Sedan だけとし、バス・トラックは
  常に一般車 (遮蔽体) として振る舞う。
- 車種構成は **通信対象を含めた全交通** の構成比。`target_ratio` は「乗用車のうち通信対象の割合」
  ではなく「全交通のうち」と定義し、`can_be_target: false` の車種を除いた中から抽出する
  (=対象車は必ず乗用車になり、乗用車全体に占める対象比は `0.30/0.80 = 37.5%`)。
- **同一 run_idx なら方式によらず同じ交通実現** (CRN)。シードは既存規約に `+30 traffic` として実装済み。
- 到着時刻 t の車は「開始時に入口の v·t 手前に置く」既存トリックで表現 (ランタイムのスポーン機構は不要)。

#### ⚠ エンティティ生成順が先着順 (FCFS) に系統バイアスを生む

`greedy_fcfs` (§4.1) の「先着」は、gz-sim が各物理ステップで**プラグインをエンティティ順に
逐次実行する**ことで決まる。現行 `traffic_gen` は **車線ごとにループして生成する**ため、
エンティティ順が `近車線の全車 → 奥車線の全車` となり、同時刻に閾値を跨いだ場合は
**常に近車線が勝つ**。これは「奥車線が不利」という本シナリオの主張に対して交絡する。

→ **展開後のエンティティ列を到着時刻順にインターリーブする** こと (§7 A5)。



### 2.2 都市部の車種構成 (初期値の根拠)

「トラック・バス・一般車の一般的な都市環境の割合」として、大型車混入率 15〜20% を中心に置いた:

| 車種 | 比率 (既定) | 寸法 [m] | 車高 | 損失 [dB] | 遮蔽するか |
|---|---|---|---|---|---|
| 乗用車 (Sedan) | 0.80 | 4.5 × 1.8 × 1.5 | 1.5 | 8 | しない (視線下) |
| トラック (Truck) | 0.15 | 12.0 × 2.5 × 3.8 | 3.8 | 26 | する |
| バス (Bus) | 0.05 | 11.0 × 2.5 × 3.2 | 3.2 | 22 | する |

掃引プリセット (大型車比率 = 遮蔽発生率の主要つまみ):

| preset | Sedan / Truck / Bus | headway mean [s] | 想定 |
|---|---|---|---|
| `free` | 0.90 / 0.07 / 0.03 | 10.0 | 郊外・自由流 |
| `urban` (既定) | 0.80 / 0.15 / 0.05 | 5.0 | 都市部幹線 |
| `congested` | 0.65 / 0.25 / 0.10 | 2.5 | 混雑・大型車多 |

### 2.3 ⚠ 需要と供給のバランスが現行と逆転する

RSU 4 台に対し、通信窓 (実効コリドー ≈ 60 m) 内に同時に存在する対象車の期待値は

```
N_concurrent ≈ (対象車到着率 λ_t) × (滞在時間 60/v)
             = (2車線 / headway 5s × 0.30) × (60 / 16.7)
             = 0.12 /s × 3.6 s ≈ 0.43 台
```

→ **RSU 4 台に対して対象車が 0.4 台** = 供給過多。現行 road_10car の「需要超過 (10台 vs 3RSU)」
とは真逆になり、公平性・飢餓の議論は成立しなくなる。研究の主張は
**「NLOS 区間の回避と HO タイミング」** に移る (それ自体は本シナリオの狙いと一致)。

需要超過も見たい場合のつまみ (どれかを効かせないと RSU が遊ぶ):

| つまみ | 例 | N_concurrent |
|---|---|---|
| 混雑 (低速化) | v = 5 m/s, headway 2.5 s | ≈ 2.9 台 |
| 対象車比率↑ | target_ratio = 0.8, headway 2.5 s | ≈ 2.3 台 |
| 車線数↑ (2+2) | 4車線 × headway 5s × 0.3 | ≈ 0.9 台 |
| コリドー拡大 | RSU 間隔を 10 → 20 m | 比例増 |

→ **`load` を独立した掃引軸とする (確定)**。3 条件を次のように定義する:

| load | 車速 | headway (両車線) | target_ratio | N_concurrent | 意味 |
|---|---|---|---|---|---|
| `under` | 16.7 m/s | 5.0 s | 0.30 | ≈ 0.4 | 供給過多。自由流。RSU が遊ぶ |
| `matched` | 11.1 m/s (40km/h) | 3.0 s | 0.50 | ≈ 1.8 | 需給均衡 |
| `over` | 5.0 m/s | 2.5 s | 0.60 | ≈ 5.8 | 需要超過。混雑。現行 road_10car に相当 |

`greedy_fcfs` の独占が問題になるのは `matched` / `over` であり、**`over` が主張の本命**。
`under` は「独占が起きない領域では提案手法の利得も消える」ことを示す対照条件として持つ。

## 3. チャネル・リンクパラメータ (現行踏襲)

| 項目 | 値 | 出典 |
|---|---|---|
| 周波数 / 帯域 | 60 GHz / 100 MHz | production_sim_spec §4 |
| 送信電力 | −7 dBm | 同上 |
| レート写像 | Shannon (noise floor −95 dBm, η=1.0, SNR cap 50 dB) | `rate_model.type: shannon` |
| 指向性 | 実測 E/H 面パターン (ピーク 22 dBi)、両端積 | 既存 |
| 持続シャドウ | FrozenField σ=4 dB, 相関長 6 m, `environment_seed` 固定 | 既存 |
| 高速フェージング | 無効 | 既存 |
| 遮蔽 | 二値 OBB、合計損失上限 60 dB | 既存 |
| リンク確立時間 | 2 ms | 既存 |
| 測定レポート | 20 Hz, 雑音 2 dB, grant 対のみ | 既存 |
| 通信計算間引き | 5 ms (200 Hz) | 既存 (P6) |

シャドウ場の `u_min/u_max` は走行域が変わるため **再計算が必要** (生成ツールが自動で行う)。

### 3.1 ⚠ 接続閾値 `rssi_min` の設計 — 本シナリオで最も効く定数

`greedy_fcfs` (§4.1) は「RSSI が閾値を跨いだ瞬間に接続し、閾値を割るまで RSU を占有し続ける」
ため、**閾値が占有時間を直接決め、独占の深刻さを決める**。閾値はコードでは
`comms_env.GetRssiMin()` = レートモデルの `MinRssiDbm()` から来る。

| レートモデル | `MinRssiDbm()` | 閾値でのレート | 備考 |
|---|---|---|---|
| `mcs_table` (既存 CSV) | **−68.5 dBm** | 0.5 Gbps | 「スループットテーブルの下限値」そのもの |
| `shannon` (本番既定, `snr_min_db: 0`) | **−95.0 dBm** | 0.1 Gbps | 実質「圏内なら常に接続可」 |

本番仕様は Shannon を採用しているが、`snr_min_db: 0.0` のままだと閾値が −95 dBm となり、
**遠方から RSU を掴んで区間を通過し終わるまで離さない**という極端な独占になる
(独占の悪さを誇張してしまい、比較としてフェアでない)。

→ **確定: Shannon を維持したまま `snr_min_db` を MCS テーブル下限と等価な値に設定する。**

```
snr_min_db = (−68.5) − (−95.0) = 26.5 dB      → rssi_min = −68.5 dBm
このときの Shannon レート = 100MHz · log2(1 + 10^2.65) ≈ 0.88 Gbps
                                       (MCS 表の 0.5 Gbps と同程度 = 整合)
```

- 両端ボアサイト時の到達距離の目安: −68.5 dBm ≈ **65 m**。ただし H 面パターンが急峻なため、
  実効的な占有窓は指向性で決まり、δ=45° 幾何では Δx ≈ ±L (奥車線で ±8 m 程度) になる。
  なお RSU を y=6.0 に近づけたことで最近接距離が縮み (奥車線で約 7.9 m)、
  ボアサイト時 RSSI は **−49 dBm 前後** = 閾値 −68.5 dBm に対して 20 dB 近い余裕がある。
  **閾値割れは距離ではなく指向性の外れと遮蔽で起きる** — これは狙いどおりの設計。
- `snr_min_db` は **感度解析の掃引変数**として残す ({16.5, 26.5, 36.5} dB = 閾値 −78.5 / −68.5 / −58.5)。
  閾値を上げるほど占有窓が短くなり、独占の害と提案手法の利得の両方が縮む — この単調性を
  示せると「結果が閾値の恣意的選択に依存しない」ことの説明になる。

## 4. 比較する方式 (arm)

本シナリオで取りたいデータは **2 極の比較**。KKF 系はこの 2 極の間のどこに落ちるかで評価する。

| arm | 呼称 | 情報 | HO / 調停 | 実装状況 |
|---|---|---|---|---|
| `greedy_fcfs` | **先着占有・HO なし (下界)** | 実測 RSSI のみ (自車の現在値) | **一切しない**。閾値超過で即接続、閾値割れまで占有 | **実装済み** (未コミット) |
| `kkf_conv` 他 | **提案手法** | grant 対のみ観測 + 学習 REM | MPC + Hungarian | 既存 |
| `oracle_inst` | 全対現在真値・貪欲 (参考) | 全対の**現在**真値 (雑音 0)。将来は知らない | 貪欲 + Hungarian | 既存 `control_plane: oracle` |
| `ff_lut` | 静的最適 LUT (参考) | 決定論成分 (距離+両端指向性) の完全知識。遮蔽・シャドウ不可視 | 位置ごとの最良ペアへ随時切替 | 既存 `feedforward_optimal` |
| ~~`oracle_pf`~~ | ~~事後最適 PF (神視点)~~ | — | — | **保留** (§4.2) |

主軸は **`greedy_fcfs` (下界) → 提案手法** の 2 点で、主張は「先着占有に対する改善幅」。
`oracle_inst` / `ff_lut` は参考腕であり、**いずれも「真の最適」を主張しない**
(前者は将来を知らない貪欲、後者は遮蔽を知らない静的最適)。この位置づけを崩さないこと。

### 4.1 `greedy_fcfs` (HO を一切行わない先着占有方式) — 下界

IEEE 802.15.3e の P2P (ペアネット) 動作に忠実な素朴方式。**1 つの RSU は同時に 1 台としか
ペアネットを張れない**ため、先に接続した車が他の (より条件の良い) 車がいても RSU を占有し続ける。
この **通信リソースの独占**を、予測と調停によって解消できることを示すのが本研究の主張。

規則 (実装 `TxControllerPlugin.cc:749`):

1. 自車の**実測 RSSI のみ**を見る。LUT も予測も他車の情報も持たない。
2. 現在接続中の RSU が `RSSI ≥ rssi_min` (§3.1) を満たし、かつ占有を保持できている間は **維持** —
   より良い RSU が空いていても切り替えない (proactive HO なし)。
3. 維持できなくなったら、**他車が占有していない RSU** のうち `RSSI ≥ rssi_min` を満たす
   最良のものへ接続する。1 つも無ければ **未接続** のまま待つ。
4. 車間の排他は `BsOccupancyRegistry` (プロセス内 singleton) が担う。「先着」は
   gz-sim のエンティティ逐次実行順で決定論的に定まる (→ §2.1 の順序バイアスに注意)。

現行実装との差分 (要確認):

- 実装は「閾値を超えた**最良の**空き RSU」を選ぶ。「閾値を跨いだ**最初の** RSU」との違いは、
  同一 comms tick (5 ms) 内に複数 RSU が同時に閾値を跨いだ場合のみ。実質的な差は小さく、
  最良選択の方が下界として不必要に弱くならないため **現行実装のままとする**。
- 接続後に閾値を割って別 RSU へ繋ぎ直す動作は「HO」ではなく **再アソシエーション** と定義する
  (802.15.3e ではリンク断からのペアネット再確立に相当)。指標上は `ho_count` に計上されるため、
  **`reassoc_count` として別集計する** (§7 E5)。

### 4.2 事後最適 (神視点) — **保留 (2026-07-27 決定)**

**「それが本当に最適か」の議論の余地が大きすぎるため、今回のスコープから外す。**

外す理由 (再検討時のために明記しておく):

- 「最良」の定義が目的関数の選択 (総量 / max-min / PF / 効用の重み) に依存し、**どれを選んでも
  恣意的**という批判を受ける。上界として提示する以上、この恣意性は主張の弱点になる。
- スロット化・切替コストの扱い・時間共有の緩和ギャップなど、**近似の入る箇所が多く**、
  「厳密な上界」と言い切れない。緩和上界と実行可能解の差を毎回説明する必要が生じる。
- 実装コストが本仕様の中で最も高い (記録 → 求解 → 再生の 3 パス + 新規ツール)。
  下界と提案手法だけでも主張は成立するため、費用対効果が悪い。

代わりに **参考上界として `oracle_inst` (全対の現在真値・貪欲) を使う**。これは
「将来を知らない貪欲」であり最適性を主張しないため、上記の批判を受けない。既存実装で回せる。

<details>
<summary>再検討する場合の設計メモ (実装しない)</summary>

3 パス構成 (記録 → 求解 → 再生)。記録は `observe_all_pairs: true, noise_std_db: 0` でほぼ足りる。
PF 目的 `max Σ_i log(R_i)` は時間方向に分離しないが、時間共有に緩和すると凹最大化になるため
**Frank-Wolfe** で解ける — 重み `w_i = 1/R_i` で線形化すると線形オラクルがスロット分離し、
**各スロットのハンガリアン法**に帰着する (PF スケジューリングの標準形と同一構造)。
緩和解が上界、反復途中の整数解が実行可能解。対象車の運動は方式に依存しない (等速ウェイポイント)
ため、記録パスは (条件, run) ごとに 1 本で全 arm に使い回せる。

</details>

| HO 回数 / 再アソシ回数 | events の非 measure 遷移を、**能動的切替**と**リンク断からの再接続**に分離 | `greedy_fcfs` は HO = 0、再アソシ > 0 になるはず (自己検証) |

## 6. 計測の回し方 — 「区切りループ」vs「1 本長回し」

### 結論: **区切り (= 1 run) のループを推奨。ただし 1 run を定常流の窓にする。**

| | 区切りループ (推奨) | 1 本長回し |
|---|---|---|
| 方式間比較 | **CRN で run 単位に対応が付く** (同一交通実現) → ペア Wilcoxon がそのまま使える | 対応が付かず、ブロック分割で分散推定するしかない |
| 既存資産 | manifest / parquet / analyze / verify がそのまま使える | 集計を作り直し |
| 閉ループのばらつき | 既知 (run 単位 3〜33%)。**分布比較が必須なので複数 run は元々必要** | 1 本では分布が取れない |
| 失敗耐性 | 1 run 落ちても再実行 | 全損 |
| 収束確認 | run を足すごとの標準誤差で判定 (自動化しやすい) | 時間方向の定常性判定が必要 |
| 壁時計 | 並列 4 で稼げる | 直列 1 本 |

**設計**: 1 run = `window_s` 120 s の定常流 (先頭 `warmup_s` 10 s は集計除外)。
1 run あたり対象車のパス数は 2 車線 × 110 s / 5 s × 0.30 ≈ **13 パス**。
これを N run 繰り返し、**主要指標の 95% CI 幅が閾値を切った時点で打ち切る** (逐次停止)。

壁時計の見積り (現行 RTF ≈ 0.22、コリドーゲーティング導入後は同等以上と仮定):

```
1 run = 60 s / 0.22 ≈ 4.5 分
arm 数 = greedy_fcfs / kkf_conv / oracle_inst / ff_lut = 4
4 arm × load 3 条件 × N=40 run = 480 run → 並列 4 で ≈ 9 時間
```

大型車比率は主張の軸ではなく感度解析なので **`urban` 固定**とし、本命条件が出てから追加する。
N は段階的に積む (N=15 で方向性を確認 → 有望な条件だけ N=40 まで) 運用を **逐次停止 (E3) と併用**。

→ **確定: window_s = 60 s (warmup 10 s)、N = 40、load 3 条件、大型車比率 `urban` 固定、arm 4 本。**

パラメータを調整する。**ここで独占が出ないなら研究の前提が崩れるので、最優先の関門**。

### 未決定

0. **RSU アンテナ高 2.5 m の再検討** (§1.2): 歩道上のポール設置としては低く、実勢は 3.0〜4.5 m。
   **3.5〜4.0 m にすると「大型車のみ遮蔽」がパラメータの微差に依存しなくなる**ため推奨だが、
   2.5 m は【実測】値なので **何を測った値かを確認してから**変更したい。
0'. **乗用車の車高 1.5 m** (§1.2): 視線との余裕が 0.18 m しかなく、ミニバン・SUV (1.7〜1.9 m) を
   含めると遮蔽側に転ぶ。(a) 1.5 m 固定で「低車高乗用車の仮定」と明記 / (b) セダンとミニバンに
   クラス分割 / (c) RSU 高を上げて問題ごと解消、のいずれか。**(c) を採れば 0' は自動的に片付く。**
1. **RSU 間隔 10 m の妥当性**: 4 台で 30 m しかなく、60 km/h では全区間を 1.8 s で通過する。
   δ=45° にすれば窓は分離できるが、1 パスの配信量が小さくなり、PF の log が小さい値に
   敏感になる。**`load: over` (5 m/s) では 6 s になるので本命条件では問題は小さい**が、
   間隔は掃引変数として残すことを推奨。
2. **既存 KKF 系 arm をどこまで回すか**: 回すなら学習相 (`sim.py learn`) を新シナリオで
   やり直す必要がある (REM 状態は幾何・環境に固有)。神視点を外したことで
   **上界が曖昧になった分、提案手法の位置づけは「`greedy_fcfs` に対する改善幅」で語る**ことになる。
   まず `greedy_fcfs` 単独で独占が観測できることを確認し (実装順序 4)、その後に提案手法を投入する。
3. **`greedy_fcfs` の再アソシエーション頻度**: 閾値を割った直後に別の空き RSU へ即再接続すると、
   実質的に「反応的 HO」に近い振る舞いになりうる。再接続にホールドタイム (例 50 ms) を
   課すか否かは、実測の `reassoc_count` を見てから判断する。
4. **`under` 条件の扱い**: RSU が遊ぶ条件では独占も提案手法の利得も消えるため、
   結果が「差なし」になる。これを対照条件として積極的に報告するか、掃引から外すか。
