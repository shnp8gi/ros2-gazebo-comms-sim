結論
・スロット長: 1byteという欄幅と物理的な時間範囲は規定されている。
  1byteへ格納する倍率・分解能は、今回確認した本書の関連箇所で明示を確認できなかった。
  0.1us単位で105とする現在の符号化を、規格から一意に導出できたとは言えない。
・Expected RSSI: 意味、1dB分解能、範囲、計算例、受信アンテナの補正は記載されている。
  範囲表記が1byteで表せる値数と整合せず、code=30-RSSIの変換式は明示を確認できなかった。
・サブヘッダーCRC8: 対象24bit、多項式、反転、MSB firstは明確に記載されている。
  回路初期値の明示は図を含む確認範囲で見つからなかった。ただし数式による剰余定義があるため、
  『CRC8自体が未規定』『初期値を自由に選べる』という結論にはしない。

1. スロット長
  確認済み根拠
  a) §6.3.1.2 / Figure 6-56、本文145 / PDF146
     Duration of an Association Slot の欄幅は1 octet。
     短い引用: “This value is the same as pDAccessSlot.”
     時間長を表すことと参照パラメータ名は確定するが、格納整数から時間への倍率はここにない。
  b) §7.20 / Table 7-13、本文348 / PDF349
     HRCP-SC用のpDAccessSlotは8.5us～10.5usの範囲。
     pMaxAssocReqCommandTime=8us、SIFSとの和として定義される。
     この表は物理時間を定める。1byteのwire表現を0.1us単位とする文言は確認できない。
  c) §5.4.2 / Table 5-30、本文108 / PDF109
     macDurAssocSlots: 1 octet、定義は “Duration of an association slot.”、Read Only。
     PIB（PAN Information Base:管理情報ベース）の項目にも、単位・倍率は記載されていない。
     PDF109の表を画像でも確認済み。
  d) §4.1.1～4.1.3、本文42～43 / PDF43～44、§6.1
     数値は別指定がなければunsigned integerで、数値のbit/octet順は定義される。
     しかし、この共通規則だけでは1us、0.1us等の時間倍率を決定できない。
  e) §6.4.13、本文177 / PDF178
     Supported SIFSについては0.1us単位のunsigned integerと明記され、0.9usの符号例もある。
     これはSupported SIFS欄の定義であり、別欄のDuration of an Association Slotへ
     同じ符号化を適用する明示的な相互参照は確認できなかった。

  判断
     「スロット時間が不明」ではない。時間範囲は分かる。
     未確定なのは、その時間を1byteへ符号化する単位。
     現在の105という値はユーザー承認の暫定方式として維持するのが適切。
     『規格全体に規定が存在しない』との不存在証明まではできていない。

2. Expected RSSI（Expected Received Signal Strength Indication:期待受信信号強度）
  注: RSSIの展開は本書の略語表のreceived signal strength indicationに合わせた。
  確認済み根拠
  a) §6.3.1.2 / Figure 6-56、本文145 / PDF146
     Expected RSSIの欄幅は1 octet。
  b) 同節、本文146 / PDF147
     短い引用: “resolution of this field is 1 dB”
     範囲表記は[+30 to −226]dBm。PDF147の画像でも−226であり、抽出テキストの誤読ではない。
     両端を含めて1dB刻みに並べると257値となり、1byteの256通りとは整合しない。
     どちらかの端点が除外される、端点の誤記、特殊値がある等の可能性は残るが、本書の
     当該箇所からどれかに確定できない。
  c) 同節のNOTE 2とその後の本文、本文146 / PDF147
     PRC側でEIRP−Path Lossにより求める計算例がある。
     DEV側の受信アンテナ利得とケーブル損失を考慮してRequest送信可否を比較する記述もある。
     これらは物理的な受信電力と比較条件を定める。unsigned codeへの変換式とは別である。
  d) §4.1.1、本文42 / PDF43
     別指定がなければunsigned integerという共通規則がある。
     この規則だけでは負のdBm値を格納するオフセットや正負方向を確定できない。
     signed 8bitをそのまま使っても−226は表現できず、不整合は解消しない。
  e) 別のRSSI定義も確認
     §6.5.10.6 / Table 6-56、本文243 / PDF244のArray Training Feedbackは
     0x00=未受信、0x01=−71dBm、0x3E=−10dBmという個別の明示的な表を持つ。
     §11.6.6、本文413 / PDF414のReceiver RSSIは2.4GHz PHYの別定義。
     これらをExpected RSSIへ流用する相互参照は確認できない。

  判断
     code=30−RSSIという現方式は、コード0を+30dBmへ対応させるという追加解釈を含む。
     この式の範囲は+30～−225dBmであり、原文の下端−226dBmを満たすものではない。
     現方式が規格の意図した符号化だと断定しない。
     「Expected RSSIの意味・計算法が未規定」という説明は誤り。
     未確定なのはwire値への対応と、範囲の端点不整合の解消方法。

3. サブヘッダーCRC8
  CRC: Cyclic Redundancy Check（巡回冗長検査）
  HCS: Header Check Sequence（ヘッダー検査系列）
  確認済み根拠
  a) §6.3.6.1 / Figures 6-71～6-72、本文155 / PDF156
     Subframe Informationは3 octets、Subheader HCSは1 octet。
     対象はヘッダー24bit、多項式はx^8+x^2+x+1。
     短い引用: “one’s-complement of the remainder”
     従って多項式0x07と最後の反転は単なる仮定ではなく、規格本文に根拠がある。
  b) Figure 6-73およびその後の本文、本文156 / PDF157
     D^6、D^1、D^1の遅延素子、排他的論理和、One’s complementの図を画像で確認。
     図中にregisterの初期値やpreset値を指示する注記はない。
     短い引用: “is transmitted with MSB first.”
     HCSの送信順は§6.1の例外として明確に定められる。
  c) §6.2.11.3.1 / Figure 6-27、本文134 / PDF135
     別のlow-latency MSDU subheaderのCRC8も同じ多項式/補数の記述と類似図を持つ。
     こちらにも今回の確認では初期値指定を見つけられなかった。
     対象は16bitであり、今回のPairnet subheaderの24bitとは異なる。
  d) 他のCRCの初期値規定との区別
     §6.2.10.6、本文128 / PDF129のFCS32は初期remainderをall onesと明示。
     §11.2.9 / Figure 11-1、本文388 / PDF389のCRC16にもall onesを明記。
     これらは各CRCの定義であり、『本書のCRCはすべてall ones』という共通規則ではない。
     サブヘッダーCRC8へ初期FFを移植する根拠にはならない。

  判断
     初期register=0を明文で確認できたとは言えない。
     一方、ゼロ初期状態は、先行データのない多項式除算として読む際の自然な候補である。
     本文に数学的な剰余定義がある以上、初期値注記がないことだけから
     「仕様が自由」「実機を測らないと原理的に計算できない」と結論しない。
     現在の初期0はユーザー承認の解釈として明示し、独立した除算/図の手順と既知bit列で
     照合する扱いが適切。今回、完全なCRC8の規定入出力例は本書で確認できていない。

5. 追加: CRC8のaugmentationとFigure 6-73の独立数式照合
  本項は上記3の「初期0の解釈」だけでは十分でない点を補う。
  初期状態0、入力24bitの最初のbitをx^23係数とするD(x)、
  G(x)=x^8+x^2+x+1を用いる。補数は8bit全体のXOR 0xFFを表す。
  実装への入力byteは各byteのLSBから処理されるため、通常のbyte列を連結した
  16進整数とD(x)の係数表現は異なる点に注意する。

  5.1 現行コードが計算している式（確定）
    src/comms_sim_pkg/src/hrcp_codec.cpp のcrc()とSubheaderCrc()を確認。
    f = input_bit XOR register[7]
    register = ((register << 1) AND 0xFF) XOR (f ? 0x07 : 0)
    という更新を24回行い、最終registerを反転する。
    初期0の場合、これは HCS = 0xFF XOR rem(D(x)*x^8, G(x)) である。
    入力に明示的な8個の0を付けていなくても、この更新形では数学的にx^8が入る。
    24bit値0..65535と、固定seedで選んだ24bitの10000値（計75536入力）について、
    整数多項式の独立した長除算と一致することを確認した。

  5.2 本文の字義に基づく別解釈（条件付き）
    §6.3.6.1、本文155 / PDF156には、24bits of the headerをGで割った剰余の補数
    とある。x^8を掛ける、8個の0を付加する、という記載は当該段落にない。
    この24bitそのものをD(x)と解釈すれば、HCS = 0xFF XOR rem(D(x), G(x))
    となり、現行式と一般に異なる。
    ただしCRCの記述上、拡張された多項式を意図して省略した可能性までは排除できない。
    この段落だけで現行式を誤りと断定しない。

  5.3 Figure 6-73の回路として確定できることと不足すること
    原本PDF157を再確認。図の矢印は右端のD^1から左向きに進み、
    左端XORの出力fが、右端D^1と2個の中間XORへ帰還している。
    その配線をゼロ初期状態の同期遅延回路として読むと、
      f[t] = input[t] XOR f[t-6] XOR f[t-7] XOR f[t-8]
    となる。registerの更新は5.1のpoly0x07更新と一致する。
    従って、24クロック後の8bit状態はrem(D(x)*x^8,G(x))を保持する。

    しかし、図のOutput dataは最終registerを直接読む端子ではなく、
    左端XORの出力fを反転した端子である。これをそのまま動作させると各クロックに
    1bitが出続ける。どの8クロックをHCSとして採用するか、入力終了後に帰還を
    切って状態を読み出すか、0入力でさらに回すか、といった制御が図に描かれていない。
    したがって「図の帰還配線が同じ」から「現行の最終状態8bitを送る処理まで
    図と完全一致」とは結論できない。

    例えば帰還を有効にしたまま0を8bit追加した際のOutput dataは、一般に
    最終状態の単純なMSB-first読み出しとは一致しない（下表の0x123456を参照）。
    データ24クロックの最後の8出力を選ぶ方法も、字義上の剰余とは一般に一致しない。
    図を実行可能な手順へ変換するには、この出力時機・読み出し方法を確定する必要がある。

  5.4 再現用24bit例（いずれも自作照合例であり規格掲載のテストベクトルではない）
    D係数表現  実装へ渡すbyte列  本文字義HCS  現行HCS  図の入力中末尾8出力  図の後続0入力8出力
    0x000001   00 00 80          FE           F8       FE                    F8
    0x800000   01 00 00          49           F4       4A                    F4
    0x123456   48 2C 6A          58           83       5B                    82
    0xFFFFFF   FF FF FF          24           F0       26                    F0
    すべてHCS/出力欄は最後の反転を含め、MSB-firstの8bitを16進表記した。
    回路初期状態は0。後続出力の計算では帰還配線を変更せず0入力を8回与えた。
    例D=1では、D mod G=1、(D*x^8) mod G=7なのでFEとF8の相違を手計算できる。

  5.5 追加判断
    ・現行式がaugmentation付きであることは確定できる。
    ・本文を24bit多項式そのものの除算と読む場合には、現行式と不一致がある。
    ・Fig6-73は現行の帰還更新を支持するが、Output dataの取り出し手順まで確定しない。
    ・したがって、現状を「初期0だけが暫定で、残りのCRC計算法は完全確定」と表すのは不適切。
      augmentationと出力抽出も照合対象として明記すべきである。
    ・上の確認だけでコードを無条件にD mod Gへ変更することも推奨しない。
      公式テストベクトル、正誤表、規格側の解釈回答等があれば、両候補を直接照合できる。
      それらは今回未確認。コード変更は行っていない。
